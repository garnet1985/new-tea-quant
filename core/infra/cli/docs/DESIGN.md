# CLI — 设计

**版本：** `0.4.0`

记录双入口、门面类（Facade）导出与命令行参数（argv）脚手架等选型。术语见 [glossary.yaml](../glossary.yaml)。相关：[ARCHITECTURE.md](./ARCHITECTURE.md)

---

## 设计点 1：双入口，不合成一个二进制

### 设计初衷

用户命令与开发 / 运维命令受众不同，需要清晰的产品边界。

### 设计背景

合并为单一入口时，短别名已冲突（如 `ex`）；帮助文案与默认命令集合也不同。历史上曾有独立 `infra.devcli` 包，后代码并入本模块但入口脚本仍分两套。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：单一二进制 | 一套 argv，用子命令或旗标区分 | 入口少 | 短别名冲突难解；帮助噪音大 |
| B：双入口 | 保留 `cli.py` / `devcli.py`，代码在 `infra.cli` | 受众清晰；别名可独立 | 两个入口脚本 |

### 决定

- **采用：** 方案 B
- **理由：** 受众与别名表本就不该强行合并
- **影响：** 调用方记住两个入口；实现共享 `Cli.shared`

## 设计点 2：只导出（export）门面类 `Cli`

### 设计初衷

符合核心模块「单一门面」约定，避免多入口点。

### 设计背景

早期可能存在 `main` / `expand_argv` 等自由函数式公开面，与「单一入口类」冲突。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：导出函数 + 类 | 兼容旧调用 | 迁移成本低 | 多真源、难收紧 |
| B：只导出 `Cli` | `__all__ = ["Cli"]`；调用一律 `Cli.user.*` 等 | 契约清晰 | 调用方一次性改 import |

### 决定

- **采用：** 方案 B
- **理由：** 对齐核心模块准则；测试只钉门面类
- **影响：** 无函数式兼容层

## 设计点 3：shared 是 namespace，不是独立产品

### 设计初衷

user / dev 都需要短别名展开与 help 判定，避免复制粘贴。

### 设计背景

若拆成第三套「shared CLI」产品，易被误当成第三入口。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：独立包 / 第三入口 | 单独产品化 | 可被外部 CLI 复用叙事强 | 产品面膨胀 |
| B：挂在 `Cli.shared` | 仅脚手架 API | 边界清楚 | 外部复用需经门面类 |

### 决定

- **采用：** 方案 B
- **理由：** shared 只服务双入口，不是第三套 CLI
- **影响：** 公开面仍只有 `Cli`

## 设计点 4：删除 `infra.devcli` 与无兼容层

### 设计初衷

代码合并到 `infra.cli` 后去掉双包与代理。

### 设计背景

维护独立 `infra.devcli` 与旧函数导出会双倍成本，且与「只导出门面类」冲突。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：保留兼容 proxy | 旧 import 仍可用 | 短期平滑 | 永久双源 |
| B：一次性切换 | 删包与自由函数导出 | 干净 | 调用方需改 |

### 决定

- **采用：** 方案 B
- **理由：** 核心模块不保留向后兼容 proxy
- **影响：** 一律 `from core.infra.cli import Cli`

## 设计点 5：短别名与 bootstrap 行为

### 设计初衷

降低常用命令输入成本；用户入口在未装好环境时尽量自举。

### 设计背景

user / dev 各自维护 `SHORT_TO_LONG`；允许同名短别名语义不同。user 需要 venv 重入与 install 门闸，dev 不需要同等 bootstrap。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：统一一张别名表 | 全局 SHORT_TO_LONG | 简单 | 无法表达冲突别名 |
| B：分表 + shared 展开 | 各入口自有表，共用 `expand_argv` | 灵活 | 两套表需各自维护 |

### 决定

- **采用：** 方案 B
- **理由：** 与双入口决策一致
- **影响：**
  - 首 token 在表中则替换为长命令，再交 argparse；空 argv / `-v` / `--version` → `version`
  - dev 的 `pack` 可经 `after_expand` 支持 `-core_vX.Y.Z` → `--version X.Y.Z`
  - user bootstrap：非 venv 且存在 `venv/` 时 `os.execv` 重入；非 early 命令按需 `install.py`；early 含 `update` / `version` / 策略 import|export、help、`-n` 新建等
