# Progress — 设计与决策

**模块：** `infra.progress` · **版本：** `0.2.3`

**最低支持核心版本：** `>=0.6.0`

本文记录本模块的设计目标、方案思路与拍板决策（进度文件的形状和写入方式；设计点 2 起取代设计点 1 的「一份当前进度」）。
相关：[ARCHITECTURE.md](./ARCHITECTURE.md)

---

## 设计目标

- **统一进度格式**：安装、回测、数据更新和标签计算曾各自写进度，界面要认多套字段；需要按节点 id 写入统一的进度文件，供界面和 PHP 直接读取。
- **不混入业务数据**：回测和标签还要保存错误、结果和机会列表，那些不是步骤计数；进度文件若塞进这些字段，就又变成业务文件。
- **表达并发与嵌套**：多个任务会同时跑，步骤还有步骤；调用方不应该声明节点在第几层，平铺的 step / sub 表达不了安装里的导入、数据源里的页。
- **热路径低开销**：进度数字只在外部调用 tick 时改变；进程内需要立刻读到刚写入的数，磁盘可以晚一点（解析器按秒甚至更慢轮询）。
- **频道快照互补**：策略工作台、标签异步 run 等需要按 job 存一份 JSON 快照（phase / label），与树形 ratio 进度互补，但不能再开第二个 infra 导出入口。

## 方案与思路

### 所有业务是否共用一份当前进度

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：一份当前进度 | 只记步骤和子步骤 | 界面一条式子 | 不保留上一份任务 |
| B：每个任务一个文件 | 按任务种类分文件 | 可以同时看多份 | 界面继续分叉 |

拍板见下文 DEC-01（后续被 DEC-02 的「一个根节点一份文件」取代）。

### 节点结构：同一种节点，按 id 查找

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：同一种节点嵌套 | steps 里只放进度节点，按 id 递归查找 | 格式统一，可以多层 | id 必须唯一 |
| B：步骤用另一种结构 | 根和步骤字段不同 | 根文件更短 | 扩展时要改两处 |

拍板见下文 DEC-02。

### 写盘策略：合并写盘 vs 每次落盘

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：合并后写盘 | 连续 tick 先改内存，再把最后一版写入 | 读接口即时，写盘更少 | 进程突然退出会丢掉还没刷出的一次 |
| B：每次 tick 都替换文件 | 调用返回时磁盘已是新的 | 崩溃也停在最后一次 | 热路径写盘更勤 |

拍板见下文 DEC-03。

### 频道快照的承载方式

若在 infra 再导出 `ProgressRecorder`，或把 `strategy-scan` / `tag-run` 等 channel 名写进 infra，会违反 Facade 单一入口，并让业务语义渗进基础设施层；tag 若 import strategy 的 recorder，又会形成跨业务依赖。

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：`Progress.channel` | 包根只导出 `Progress`；另挂 path/write/read/clear；channel 名由调用方自定 | 单一入口；infra 无业务名；tag 可直连 | 业务侧可能各自包一层约定 |
| B：infra 再导出 `ProgressRecorder` | 包根同时导出 recorder，并内置业务 channel | 调用方少写几行 | 双入口；业务名进 infra |

拍板见下文 DEC-04。

## DEC-01：设计点 1：所有业务共用一份当前进度

- **采用：** 方案 A
- **理由：** 界面只需要当前正在跑的那一次。错误和结果仍由各业务模块自己的记录保存。
- **影响：** 后开始的任务覆盖前一份进度。
- **后续：** 设计点 2 改为一个根节点一份文件。本决定不再使用。

---

## DEC-02：设计点 2：同一种节点，按 id 查找

- **采用：** 方案 A
- **理由：** 加字段时只改一种节点。tick 只带 id。
- **影响：** 有子节点的 ratio 来自子节点的 weight；叶子才用 done / total。

---

## DEC-03：设计点 3：写盘可以合并

- **采用：** 方案 A
- **理由：** 解析器不需要每一次 tick 都已经在磁盘上。日志仍在调用当次打印。
- **影响：** 没有定时器去推进进度。

---

## DEC-04：设计点 4：频道快照走 Progress.channel

- **采用：** 方案 A
- **理由：** Facade 只导出 `Progress`；infra 不写业务 channel 名；tag 可直连 `Progress.channel`，不必依赖 strategy。
- **影响：** strategy 若要包一层约定，放在**业务模块** `core/`（如 strategy 的 `ProgressRecorder`），不经 infra 包根导出。

---

## DEC-05：测试复位走门面 `reset_for_tests`

- **采用：** `Progress.reset_for_tests()` 委托内部 `store.reset`；跨模块单测不得深导入 `progress.core.store`。
- **理由：** 包根仍只导出 `Progress`；测试复位是公开契约的一部分（与 `drain` 同级），避免 Facade 侵蚀。
- **影响：** 生产勿调用；`API.md` 标注「仅单测」。
