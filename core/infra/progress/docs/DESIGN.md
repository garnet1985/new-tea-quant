## 设计点 1：所有业务共用一份当前进度

### 设计初衷

安装、回测、数据更新和标签计算各自写进度，界面要认多套字段。

### 设计背景

回测和标签还要保存错误、结果和机会列表，那些不是步骤计数。进度文件若塞进这些字段，就又变成业务文件。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：一份当前进度 | 只记步骤和子步骤 | 界面一条式子 | 不保留上一份任务 |
| B：每个任务一个文件 | 按任务种类分文件 | 可以同时看多份 | 界面继续分叉 |

### 设计初衷

多个任务会同时跑。步骤还有步骤。调用方不应该声明节点在第几层。

### 设计背景

平铺的 step / sub 表达不了安装里面的导入，也表达不了数据源里面的页。两套文件格式会让解析器分叉。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：同一种节点嵌套 | steps 里只放进度节点，按 id 递归查找 | 格式统一，可以多层 | id 必须唯一 |
| B：步骤用另一种结构 | 根和步骤字段不同 | 根文件更短 | 扩展时要改两处 |

> 本节决定已独立到 [DECISIONS.md](./DECISIONS.md)（自动编号 DEC-XX）## 设计点 3：写盘可以合并

### 设计初衷

热路径上每个计数都立刻替换文件，没有必要。解析器按秒甚至更慢轮询。

### 设计背景

进度数字只在外部调用 tick 时改变。进程内需要立刻读到刚写入的数，磁盘可以晚一点。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：合并后写盘 | 连续 tick 先改内存，再把最后一版写入 | 读接口即时，写盘更少 | 进程突然退出会丢掉还没刷出的一次 |
| B：每次 tick 都替换文件 | 调用返回时磁盘已是新的 | 崩溃也停在最后一次 | 热路径写盘更勤 |

> 本节决定已独立到 [DECISIONS.md](./DECISIONS.md)（自动编号 DEC-XX）

## 设计点 4：频道快照与树形进度并列

### 设计初衷

策略工作台、标签异步 run 等需要按 job 存一份 JSON 快照（phase / label），与树形 ratio 进度互补，但不能再开第二个 infra 导出入口。

### 设计背景

若在 infra 再导出 `ProgressRecorder`，或把 `strategy-scan` / `tag-run` 等 channel 名写进 infra，会违反 Facade 单一入口，并让业务语义渗进基础设施层；tag 若 import strategy 的 recorder，又会形成跨业务依赖。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：`Progress.channel` | 包根只导出 `Progress`；另挂 path/write/read/clear；channel 名由调用方自定 | 单一入口；infra 无业务名；tag 可直连 | 业务侧可能各自包一层约定 |
| B：infra 再导出 `ProgressRecorder` | 包根同时导出 recorder，并内置业务 channel | 调用方少写几行 | 双入口；业务名进 infra |

> 本节决定已独立到 [DECISIONS.md](./DECISIONS.md#dec-04)（DEC-04）
