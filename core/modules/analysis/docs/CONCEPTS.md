# Analysis — 概念与运作

**模块：** `modules.analysis` · **版本：** `0.1.0`

本文不给结论。只把三个还没想清的问题摊开，避免和 factor 研究、strategy 报告混在一起。  
文字入口见 [README.md](../README.md)；词条见 [glossary.yaml](../glossary.yaml)；选型过程见 [DESIGN.md](./DESIGN.md)。

---

## 本模块在链路里的位置

```text
数据契约 → 策略 hooks → 三层模拟 → 落盘报告
                              ↓
                         （本模块，未实现）
                              ↓
                      解释：inputs 与 outputs 的关系
```

strategy 的 report 回答「结果长什么样」。本模块要回答「这份结果，和这次用到的输入有多大关系」。  
`modules.strategy` 不再提供 analyze API。

---

## 问题 1：如何判断 inputs？

「输入」在 NTQ 里至少有好几层，现在没有判定规则：

| 候选层 | 直觉 | 现状 |
|--------|------|------|
| 旋钮 | settings 里的阈值、止盈止损、资金参数 | 枚举 run 的 settings 快照里可能有 |
| 数据声明 | `settings.data` 声明的 DATA_KEY / 指标 | 能还原「用了什么数据」，不是每笔的值 |
| 决策现场值 | `has_opportunity` 当时看到的 RSI、PE 分位等 | 逻辑层经 `ctx.capture` 进入内存 `Opportunity.signal_snapshot`；声明层尚未自动冻；落盘格式未定 |
| 执行与环境 | 成交价规则、股票池、回测区间 | `runtime_env` 一类元数据 |
| 代码本身 | hooks 里的 if/else | 很难当成可列表的 input |

还没有决定：归因认哪几层；没落盘的现场值算不算「本模块的输入」；声明了但没进 `signal_snapshot` 的数据算不算用过。

---

## 问题 2：如何归因？一种还是多种方法？

「归因」在这里是指：解释 outputs 随 inputs 怎么变，而不是把收益拆成市场/行业/风格（那是 factor / 风险模型）。

候选做法可以并存，也可以先只留一种——**未拍板**：

- **清单**：这次声明了什么、成交上实际出现了什么
- **决定空间**：这个输入在已触发样本里还变不变（几乎常数 → 解释不了差异）
- **共变**：有变化的输入，和 ROI / 胜负是否一起变
- **版本对照**：两次 run、一份 `settings_diff`，看输出差

未拍板的还包括：这些是一条流水线里的几步，还是用户可选的多种方法；要不要为了「去掉某道门闩会怎样」去再跑一遍 simulate（那是 strategy 的事，本模块最多读两次产物）。

---

## 问题 3：如何解释回测结果？要不要也分三层？

NTQ 的模拟本身是三层，outputs 形状不同：

| 层 | 主要在问 | 已有产物直觉 |
|----|----------|----------------|
| enumerate | 有没有机会、机会长什么样 | 机会次数、分布、生命周期 |
| price_factor | 抓住价格波动了没有（无资金约束） | 逐笔 ROI、胜率、跳过成交 |
| portfolio | 有限资金下能不能活 | 净值、回撤、成交与跳过 |

未拍板：

- 解释是否必须跟这三层一一对应（三套归因）
- 还是先只解释一层（例如价格层逐笔），组合层后补
- 或者做跨层解释（枚举很强但组合很差时，问题在信号还是在资金约束）

现有 overall report 已经按层写了。本模块若再按层切，要避免把同一套胜率数字再算一遍。

## 和未来 factor 模块

factor 问的是「这个因子在全市场有没有预测力」（分组、滚动、挖掘）。  
analysis 问的是「**这次策略 run** 的结果，和它用过的输入有多大关系」。

统计公式以后可能长得像，产品问题不是同一个。本模块不预埋 IC / 滚动回测 API。
