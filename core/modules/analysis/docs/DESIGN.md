## 设计点 1：独立模块还是放进 strategy

### 设计初衷

归因是回测之后的解释，不是 simulate 管线的一步。

### 设计背景

`modules.strategy` 已负责发现、hooks、三层模拟与报告。再塞解释器会让生产者和消费者长在同一个模块里；日后 factor / tag 若也要「解释这次用了哪些输入」，会被迫依赖整套模拟栈。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：独立 `modules.analysis` | 只读产物，门面独立 | 边界清；strategy 不再膨胀 | 多一个模块的文档/契约成本 |
| B：放进 strategy | 在 strategy 里做归因入口 | 路径短 | 职责轴错；以后难抽 |

### 决定

- **采用：** 方案 A
- **理由：** 与 BE / strategy 的「调度 vs 业务」分离同一原则；空模块成本可接受
- **影响：** `Strategy.analyze` 与 CLI `strategy_analyse` / `sy` 已删除；归因只进本模块

## 设计点 2：与 factor 模块分家

### 设计初衷

避免把「解释一次策略 run」做成「因子研究平台」。

### 设计背景

IC、滚动回测、股票分组、因子挖掘属于另一条产品线（路线图 Pro / 未建模块）。本模块若先暴露这些 API，会锁死错误问题。

### 决定

- **采用：** analysis 不提供因子研究 API；不在本模块预埋 IC / 滚动 / 挖掘入口
- **理由：** 问题不同；工具以后可以共享统计原语，产品入口必须分开
- **影响：** 本模块 glossary 将「因子」列为 avoid

## 设计点 3：如何判断 inputs（待决）

### 设计初衷

没有「什么算 input」，归因没有对象。

### 设计背景

一次 run 里同时存在：settings 旋钮、data 声明、hooks 决策现场值、执行假设、股票池与区间。现场值目前没有稳定落盘。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：只认 settings 旋钮 | 阈值、目标、资金参数 | 已有快照，好对照两次 run | 解释不了「这笔为什么买」 |
| B：只认决策现场值 | `signal_snapshot` 等每笔当时的数 | 最接近真正做决定的输入 | 要先补产物；策略作者不 capture 则空 |
| C：分层都认，规则后定 | 旋钮 / 声明 / 现场值分列 | 不丢信息 | 第一期范围容易炸 |
| D：以策略声明为准 | settings.data + core 白名单 | 和用户心智接近 | 「声明了」≠「参与了决定」 |

### 决定

- **采用：** 待决
- **理由：** 还没有判定规则，也没有约定策略必须把现场值写入产物
- **影响：** 行为 API 不能先写「factor_cols=...」这类参数

## 设计点 4：如何归因（待决）

### 设计初衷

「有关系」需要可重复的做法，而不是一篇散文。

### 设计背景

候选工具包括：输入清单、决定空间（样本内是否还在变）、共变、两次 run 对照。它们可以是一条流水线，也可以是多种方法。去掉某输入再跑一遍属于 simulate，不是本模块自己开时间轴。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：单一方法 | 例如只做两次 run 对照 | 认知负担低 | 单次 run 无法解释 |
| B：固定流水线 | 清单 → 决定空间 → 共变（→ 可选对照） | 一次分析有完整故事 | 可能对空输入过重 |
| C：多种方法并列 | 用户选工具 | 灵活 | 模块会像工具箱，解释叙事弱 |

### 决定

- **采用：** 待决
- **理由：** 方法取决于 inputs 怎么定义；先定对象再定算法
- **影响：** Facade 暂无 `attribute` / `compare` 方法，避免先锁 API

## 设计点 5：解释结果要不要分三层（待决）

### 设计初衷

strategy 的 outputs 按 enumerate / price_factor / portfolio 分家，解释层是否跟随。

### 设计背景

三层问的问题不同（有没有机会 / 价格捕获 / 资金约束）。现有 report 已按层给出总数。跨层现象（枚举好、组合差）可能才是用户真正想解释的。

### 解决方案

| 方案 | 做法摘要 | 优点 | 缺点 |
|------|----------|------|------|
| A：三套归因对齐三层 | 每层一份 attribution | 和回测心智一致 | 工作量×3；易与 report 重复 |
| B：先只解释一层 | 例如只做 price 逐笔 | 范围可控 | 组合层问题暂时看不见 |
| C：跨层解释为主 | 层与层的差异当对象 | 贴合「哪一层坏了」 | 契约更难，依赖三层都跑完 |

### 决定

- **采用：** 待决
- **理由：** 取决于第一期要回答哪一句话；不要因为模拟分三层就默认分析也分三层
