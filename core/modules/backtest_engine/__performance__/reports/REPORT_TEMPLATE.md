# 性能测试报告模版

每跑一次 `bpe` / `bps` 产出一份报告（`REPORT.md` + `metrics.json`）。  
entity 与 slice **各出一份**，格式相同；「怎么调度」那一段按模式填不同内容。

---

## 一、环境（跑在什么机器、什么库）

| 报告里写什么 | 含义 | 例子 |
|--------------|------|------|
| 操作系统 | 电脑系统 | macOS 15.7.3 |
| CPU | 处理器 | Apple M1 Max（10 核） |
| 内存 | 内存大小 | 32 GB |
| Python | 运行版本 | 3.9 |
| 数据库类型 | **必填**：duckdb / mysql / postgresql | duckdb |
| 数据库名称 | 这次用的临时库名 | perf_test_tmp |

机器信息可与《测试前提》一致；**每份报告都要写清用的是哪种数据库**。

---

## 二、结果（跑得怎样）

### 大家都要写

| 报告里写什么 | 含义 |
|--------------|------|
| 运行模式 | 按股票分包（entity）或按时间切片（slice） |
| 总执行时间（秒） | 从开始到结束，人真实等待的时间 |
| 股票数 | 这次测了多少只股票 |
| 交易日数 | 开市日有多少天 |
| 数据量（行） | 股票数 × 交易日数 |
| 处理速度 | 每秒处理多少「股票×交易日」（= 数据量 ÷ 总执行时间） |
| 是否成功 | 成功 / 失败 |

处理速度统一用上面这一种算法，方便两份报告对照。

### 调度情况（按模式）

**entity 模式（各股票可分开算，不必同一天齐步走）**

| 报告里写什么 | 含义 |
|--------------|------|
| 同时开几个进程 | 并行干活的进程数 |
| 任务包数量 | 一共拆成多少包 |
| 每包多少只股票 | 每个任务包里的股票数 |
| 并行效果 | 多进程一起跑时，相对「一个人干」快了多少（系统给出的数） |

**slice 模式（股票之间要相互对照，日历要按顺序往前推）**

| 报告里写什么 | 含义 |
|--------------|------|
| 计算用几个进程 | 一般是 1（日历要按顺序算） |
| 读数据用几个进程 | 后台帮忙预读的进程数 |
| 预读排队深度 | 最多提前准备几片数据 |
| 每片多少个交易日 | 一片覆盖的天数 |
| 一共切了几片 | 正式片数量 |
| 每只股票装载几次 | 整段回测里每只股票被装数据的次数 |

### 时间花在哪

| 报告里写什么 | 含义 |
|--------------|------|
| 准备/规划（秒） | 开始前估内存、订计划 |
| 读数据（秒） | 从数据库取数 |
| 计算（秒） | 按交易日往前推、跑策略逻辑 |
| 写报告（秒） | 落盘出结果 |

能从系统自带的 `performance.json` 里抄过来的，优先用那里的拆分。

### 并行效果

| 报告里写什么 | 含义 |
|--------------|------|
| 并行效果 | 多干活是否叠在一起、整体变快的程度 |
| 并行效率 | 有则一并写上 |

说明：slice 模式里真正按日历往前算，通常只有 1 个进程；这里的并行效果更多反映「读数据有没有帮上忙」，不要和 entity「好几个进程一起算」当成一回事。

---

## 三、给人看的报告长这样

```markdown
# 性能测试报告 — {运行模式}

## 环境
- 操作系统 / CPU / 内存 / Python
- 数据库类型 / 数据库名称

## 结果
- 运行模式
- 总执行时间（秒）
- 股票数 / 交易日数 / 数据量（行）
- 处理速度（股票×交易日 / 秒）
- 是否成功

## 调度情况
- （按 entity 或 slice 填上表）

## 时间花在哪
- 准备/规划、读数据、计算、写报告（秒 + 占比）

## 并行效果
- 并行效果 [、并行效率]
```

机器可读的 `metrics.json` 用同一套信息，方便以后自动对比。
