# 性能测试报告模版

每次 `bpe` / `bps` 会按配置最大股票数自动跑 **三档**（25% / 50% / 100%），
每档一份 `REPORT.md` + `metrics.json`，跑完写模式级 `OVERALL.md`：

```text
reports/
├── REPORT_TEMPLATE.md
├── test_preconditions.md
└── {BE版本}/                 # 如 0.4.0
    ├── entity_based/
    │   ├── OVERALL.md        # 三档趋势 + T0/k
    │   ├── N250/{duckdb,mysql,pgsql}/
    │   ├── N500/...
    │   └── N1000/...
    └── slice_based/
        └── （同上）
```

换了 BE 版本再跑，会进新目录，旧报告保留。  
同一次命令只测一个 `--db`；库之间不要混比。entity / slice 分看。

---

## 一、环境（跑在什么机器、什么库、什么版本）

| 报告里写什么 | 含义 | 例子 |
|--------------|------|------|
| 跑测时间 | 这次跑完写报告的时间（UTC） | 2026-08-06T07:24:57Z |
| 回测引擎 (BE) | 当前模块版本 | 0.4.0 |
| core | 核心版本 | 0.4.x |
| 相关模块 | 影响速度的依赖版本 | data_manager 0.4.0, strategy 0.7.0, … |
| 操作系统 / CPU / 内存 / Python | 机器环境 | macOS / M1 Max / 32 GB / 3.9 |
| 数据库类型 | duckdb / mysql / pgsql | pgsql |
| 数据库名称 | 这次用的临时库名 | perf_test_tmp |

**任何引擎或核心依赖变版本，速度都可能变**——报告必须写清版本，才能和历史档对比。

---

## 二、结果（跑得怎样）

### 大家都要写

| 报告里写什么 | 含义 |
|--------------|------|
| 运行模式 | 按股票分包（entity）或按时间切片（slice） |
| 样本档 | N250 / N500 / N1000（相对最大股票数的比例） |
| 总执行时间（秒） | 从开始到结束，人真实等待的时间 |
| 股票数 / 交易日数 / 数据量（行） | 规模 |
| 处理速度 | 数据量 ÷ 总执行时间（股票×交易日 / 秒） |
| 是否成功 | 成功 / 失败 |

### 调度情况（按模式）

**entity**

| 报告里写什么 | 含义 |
|--------------|------|
| 同时开几个进程 / 任务包数量 / 每包多少只股票 | 怎么分包并行 |

**slice**

| 报告里写什么 | 含义 |
|--------------|------|
| 计算/读数据进程数、预读排队、每片天数、片数、每只股票装载几次 | 怎么切片预读 |

### 时间花在哪（四大步 + 少量小项）

空策略下「推进日历 / 引擎开销」≠ 选股算力。

**两边都有的大项**

1. 准备/规划（秒 + 占比）→ 小项见下  
2. 读数据（秒 + 占比）→ 小项见下  
3. 推进日历 / 引擎开销（秒 + 占比）→ 小项见下  
4. 写报告（秒 + 占比）

**entity 常见小项（有数据才写）**

| 大项 | 小项 |
|------|------|
| 准备/规划 | 试跑采样（定并行）；正式规划 |
| 读数据 | 峰值内存（试跑采样）；装合约/行情 |
| 推进日历 | 填上下文；按日 as-of；合约 until；日历 tick |

**slice 常见小项（有数据才写）**

| 大项 | 小项 |
|------|------|
| 准备/规划 | 调度采样说明（正式任务前几片定宽；**不**把整次墙钟塞进准备） |
| 读数据 | 读进程峰值内存；单片读数（估） |
| 推进日历 | 计算进程峰值内存；单片推进（估）；片间序列化/反序列化（有耗时才写） |

说明：slice 没有单独「试装」阶段；`performance.json` 里 `probe.wall_sec` 是整次任务墙钟，勿当准备耗时。

### 并行效果

| 报告里写什么 | 含义 |
|--------------|------|
| 并行效果 / 并行效率 | 多干活叠在一起的程度；slice 多反映「读是否帮上忙」 |

## 三、给人看的报告长这样

```markdown
# 性能测试报告 — {运行模式} · N{样本} · {数据库目录名}

## 环境
- 跑测时间 / BE 版本 / core / 相关模块
- 操作系统 / CPU / 内存 / Python
- 数据库类型 / 数据库名称

## 结果
- 运行模式 / 样本档 / 总执行时间 / 股票数 / 交易日 / 数据量 / 处理速度 / 是否成功

## 调度情况
- （按 entity 或 slice）

## 时间花在哪
- 准备/规划 …
  - entity：试跑采样 / 正式规划；slice：调度采样说明
- 读数据 …
  - （模式相关小项）
- 推进日历 / 引擎开销 …
  - （模式相关小项）
  - 说明：空策略下不是选股算力
- 写报告 …

## 并行效果
- 并行效果 [、并行效率]
```

同模式另有 `OVERALL.md`：三档墙钟/吞吐表、T≈T0+k·N、翻倍吞吐变化%、固定成本占比、近固定/近线性判断。

`metrics.json` 与报告字段对齐，便于以后自动对比。
