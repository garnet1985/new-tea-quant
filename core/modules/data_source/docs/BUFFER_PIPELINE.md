# 抓取结果缓冲写入

**模块：** `modules.data_source` · **版本：** `0.3.0`

记录抓取结果如何进入内存、何时写入数据库。实现以 `core/service/pipeline/` 为准。

---

## 背景

2026-10-12，2 核、约 3.6GB 内存的服务器上，`cli.py renew` 拉取 2008 年至当日的全市场数据。Python 进程 RSS 约 2.45GB 时被 OOM 杀掉。该进程位于 Apache 的 cgroup 内，站点随之停止。当时无 swap。MariaDB 的 `innodb_buffer_pool_size` 为 512MB。

内存上来自两处：

1. 批次写入之外，成功结果仍留在整表结果里，直到该数据源结束。结束时再把整表转成入库记录。
2. `SaveBatchAutoSizer` 按任务个数调整批次。预算有 1024MB 下限，任务多时批次上限走向 500。它在写入完成后看 RSS 增量，看不到写入过程中 DataFrame 与整批字典同时存在的峰值。RSS 增量接近 0 时，批次继续变大。

K 线一只股票十几年的日线加周线只有数 MB。资金流向一天全市场也是数 MB。单笔返回本身不是 2GB 的来源。

---

## 方案

所有数据源走同一条写入路径：

1. 一笔请求返回后，整理成一张表。
2. 表进入缓冲区，原始返回随即释放。
3. 缓冲区达到字节上限时写入数据库。
4. 数据源结束时，把未满的剩余也写入。
5. 写入按固定行数分块，每块转成现有 `save` / `upsert_many` 需要的记录后立刻释放。

配置里不再有 `save_mode` 和 `save_batch_size`。按任务个数增长的批次计算器已删除。

---

## 内存预算

进程开始抓取时，用 `MachineInfo.virtual_memory_mb()` 读取可用内存，并沿用 `MachineInfo` 的 floor 计算必须留给系统的部分。本管道的预算是可用内存减去 floor 之后的余量，再乘以 worker 内存比例。

不套用这两处下限：

- `SaveBatchAutoSizer` 的 `max(1024MB, …)`
- `MachineInfo.MIN_BUDGET_MB`（256MB）作为「至少占用这么多」

余量很小时，缓冲区缩小，同时在飞的请求保持 1。一笔结果仍大于预算时，单独写入这一笔，并记一条警告。

每个数据源开始时重新读一次可用内存。同一数据源内，用已经映射好的表测量一笔有多大（`DataFrame.memory_usage(deep=True)`，取本源已见过的最大值）。预算 `B`、写库块预留 `W`、单笔大小 `S` 满足：

```text
buffer_cap + in_flight * S + W <= B
```

- `W` 是固定的一小块记录，不随机器变大。
- `in_flight` 至少为 1，且不超过 `cpu_count - reserve_cores`。核数只限制线程数。
- 放得下更多在飞请求时才增加 `in_flight`。增加后缓冲区至少还能放下一笔。
- 单笔变大时按上面的式子重算。写入后若进程 RSS 超过预算，把 `B` 降到实际余量。

进入缓冲区之前，若待写字节加上这一笔会超过 `buffer_cap`，先写入再放入。

写库发生在主线程。已经发出的请求仍会返回，结果停在线程池里，所以上式把 `in_flight` 算进峰值。2 核小内存和多核大内存使用同一式子。

## 表到表

映射规则的值全是列名时，在 DataFrame 上选列、改列名、写入常量列。不经过 `to_dict` 和字典列表。

规则里含按行函数的源，各自算出一张表，然后进入同一个缓冲区。空结果与 `None` 不进入缓冲区。

复权因子和 ST 区间按股票删除或替换已有行。这两处在算出该股结果后立即写入，不把多股的行混进同一块。

缓冲区保存多张已经映射的表，不把它们 `concat` 成一张大表。写入时按行窗口从这些表里取出记录，交给现有的保存函数。

---

## 依赖结果

调度器只缓存被下游依赖的执行结果。当前被其他数据源依赖的是 `stock_list` 和 `sw_industry`。这两处的返回值仍包含下游要读的 `data`。它们的体量是一份名单，不是多年 K 线。

其余数据源写入缓冲区后，返回给调度器的 `data` 为空。它们的结果不进入 `merged`。

---

## 决策

### 决策 1：一种写入路径

**决策：** 缓冲区达到字节上限就写入，数据源结束时写入剩余。不再按 `unified`、`immediate`、`batch` 分支。

**原因：** 三种模式让同一批结果既留在整表里，又按批写入。大表因此在收尾时再占一份内存。

### 决策 2：映射保持为表

**决策：** 列名映射在 DataFrame 上完成。缓冲区里只留映射后的表。

**原因：** 整批 `to_dict` 会在原始表还活着时生成一份更大的字典。

### 决策 3：预算来自机器余量，按字节拆分

**决策：** 用 `MachineInfo` 探测内存。预算拆成缓冲区、在飞请求和一块写库记录。核数只作为线程上限。

**原因：** 按任务个数和核数做机器特例，会在小内存上把批次加到 500，也会在大内存上无故限制并发。

### 决策 4：分块写入，不拼接整块缓冲

**决策：** 调用现有保存函数时只传入固定行数的记录。不把缓冲区 `concat` 或一次 `to_dict`。

**原因：** 缓冲区改成表之后，若写入前仍展开整批，峰值会回到两种形态同时存在的状态。

### 决策 5：依赖源单独返回下游数据

**决策：** `stock_list` 与 `sw_industry` 继续返回调度器要缓存的 `data`。其他源不保留整表结果。

**原因：** 下游从依赖缓存读取名单。大表不是下游依赖，没有理由为调度器留一份全集。

### 决策 6：限流等待时写入不在本次范围

**决策：** 等待接口限流时不额外触发写入。字节上限已经保证内存。

**原因：** 等待发生在抓取线程，写入在主线程，接上要另做配合。它缩短占用时间，不决定能否跑完。

## 不在本次范围

- 把 Python 移出 Apache cgroup，或调整 OOM 策略。
- 增加 swap。
- 改变 Tushare 限流与失败后续拉。失败的任务不写入，下次从各实体已有日期继续。
